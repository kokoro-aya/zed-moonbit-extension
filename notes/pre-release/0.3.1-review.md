# MoonBit Lab 0.3.1 pre-release review

Status: candidate pipeline opened  
Baseline: MoonBit `moon 0.1.20260803`, `moonc/moon-lsp 0.10.6`  
Previous accepted editor milestone: `0.3.0` usability  
Candidate manifest version: `0.3.1`

## Version reading

The independently accepted Cy3 It0 editor surface is recognized as the 0.3.0
usability milestone. No separate 0.3.0 manifest/tag is created: the manifest
moves directly from 0.2.9 to 0.3.1 so this post-review repair set is the first
pre-release candidate carrying that usability claim.

This is not a Registry publication claim. The candidate enters review through
development installation and the repository validation ladder.

## External issue triage

| Review item | Reading | Resolution / retained boundary |
| --- | --- | --- |
| LSP/task toolchain divergence | Confirmed contract ambiguity, not a need for a toolchain manager | `lsp.moonbit.binary` controls only LSP; tasks deliberately use the Zed project environment's `moon`. The README now states both authorities. |
| Unknown server requests in the LSP probe | Confirmed evidence bug | Validation is strict by default and fails with bounded request context. Exploratory `null` replies require an explicit CLI policy and remain visible in the timeline. |
| Duplicated versions and grammar pins | Confirmed release risk | The query audit parses both manifests and fails on release-version, Zed-API, or grammar-revision divergence with field-specific diagnostics. |
| Windows environment handling | Confirmed product bug | The extension no longer discards `worktree.shell_env()` on Windows; configured values override using case-insensitive environment-key identity. |
| Test runnable granularity | Confirmed UX bug | Named test declarations capture their unquoted name and invoke `moon test <file> --filter <name>`. Two declarations prove one-test selection. |
| Task root semantics | Confirmed UX bug | Current-project tasks start at the active file and delegate upward discovery to Moon; separate worktree-root tasks state the root-level manifest/workspace requirement. |
| Query tests were mostly syntactic | Confirmed test weakness | Narrow tests now assert highlight roles, delimiter pairing/properties, and indent/end structural captures. |

The first real-Zed rerun after these repairs exposed an additional transport
counterexample: Zed 1.18.1 expanded an absolute `$ZED_FILE` and a captured test
name containing spaces into shell-split arguments despite their `args` array
positions. The runnable now starts in `$ZED_DIRNAME`, uses the local
`$ZED_FILENAME`, and adds explicit shell quotes around both substituted values.
This compatibility measure remains covered by a real path containing a space.

No item required a compiler shadow, package resolver, project scanner, LSP
router, or toolchain installer. The thin-client ownership boundary therefore
survives the review.

## Portability ledger

Repository-proven:

- the production extension builds as `wasm32-wasip2`;
- language-server lookup uses Zed's worktree environment or an explicit
  standard binary setting;
- Windows environment merging treats key identity as case-insensitive;
- built-in tasks use command/argument arrays and Zed variables rather than
  POSIX shell programs;
- the pinned grammar includes a portable C external scanner and is compiled by
  the Zed development-extension workflow.

Editor-proven:

- macOS with Zed 1.18.1 and the pinned MoonBit baseline passed the complete Cy3
  It0 user gate before this review;
- after workspace reload, the 0.3.1 development extension displayed both test
  runnables; the second declaration ran exactly one test successfully, and the
  main runnable printed `geometry-library:42`, all from the repository path
  containing `PL Playground`.

Still unproven:

- a real Zed install and Moon process launch on Linux;
- a real Zed install, case-insensitive environment behavior, and task launch
  on Windows;
- Registry packaging or one-click installation;
- toolchain versions beyond the pinned baseline.

Consequently the design is cross-platform-shaped, but “another user can
install and run without friction on all three OSes” is not yet an evidence-backed
claim. Linux/Windows editor runs and Registry/repository extraction belong to
the next pre-release review gates, not to hidden logic in the extension.

## 0.3.1 gates

- full fixture format/check/test/run matrix;
- Rust format, tests, Clippy, strict manifest/query audit;
- strict native LSP capability/project-root/freshness matrix;
- release WASI component build;
- commit discipline and clean tracked/index state;
- development installation smoke test on macOS after the repair set;
- independent Linux and Windows editor evidence before a general
  cross-platform release claim.

All repository gates and the post-repair macOS development-installation smoke
gate are currently green. The final two platform claims remain deliberately
open for the next review stage.
